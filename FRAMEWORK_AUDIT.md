# Аудит QA Automation Framework

Дата: 12 ноября 2026 года. Объект: текущая реализация Playwright + TypeScript в этом репозитории.

## Общая оценка

Для учебного и портфолио-проекта архитектура разумная: сценарии описывают действия и проверки, Page Objects содержат локаторы и действия страниц, API clients инкапсулируют HTTP-запросы, fixtures управляют контекстами и авторизацией. Managers дают единый способ получить нужный объект. Здесь нет причины вводить дополнительные сервисы, репозитории данных, универсальный HTTP-wrapper или генератор Page Objects.

Проект демонстрирует рабочий вертикальный срез: регистрация → сохранение авторизации → публикация через UI → проверка ленты, плюс два API-сценария. Docker и два способа запуска в GitHub Actions, GHCR, Playwright HTML, Allure и публикация отчётов уже реализованы. Их переписывание не требуется.

Главные улучшения относятся к надёжности этого среза: отдельная проверка типов, проверка конфигурации при загрузке, более явный контракт авторизованной API-fixture, очистка собственных статей и несколько недостающих assertions. Полнота автоматизации пока небольшая: реализованы 3 из 30 описанных тест-кейсов. Это характеристика объёма демонстрации, а не требование немедленно автоматизировать остальные 27.

### Как читать выводы

- **Подтверждено по коду** — механизм или пробел виден в исходниках; это не означает, что соответствующий сбой наблюдался на приложении.
- **Проверено локально** — дополнительно выполнена проверка без обращения к приложению и без чтения реальных настроек авторизации.
- **Требует запуска** — влияние зависит от DOM, ответа сервера или поведения публичного демо; воспроизведения в этом аудите не было.
- **Контекст владельца** — сведения о периодическом удалении пользователей и статей, а также пересоздании пользователя при повторной регистрации. Они приняты как основание существующего setup, но самостоятельно не проверялись.

Все примеры ниже — предложения. Из файлов проекта создан только этот отчёт; код, настройки и тест-кейсы не изменялись. Ссылки ведут на исходники, номера строк относятся к состоянию на момент аудита.

## 1. Структура проекта и ответственность компонентов

**Как работает.** `src/realworld` разделён на `base`, `ui`, `api` и `tests`. В `ui/pages` находятся объекты страниц, в `ui/components` — навигация. В `api/clients` — клиенты пользователя и статей. User Story, тест-кейсы и OpenAPI лежат отдельно от исполняемого кода.

**Что хорошо.** По расположению файла понятно его назначение. Например, [ArticlesApiClient.ts](src/realworld/api/clients/ArticlesApiClient.ts#L16) собирает запрос, а [spec](src/realworld/tests/articles/us001-publish-article.spec.ts#L86) проверяет результат. Assertions не спрятаны в транспортном клиенте. Это позволяет использовать один клиент для подготовки данных и для проверки API с разными ожиданиями статуса.

[BasePage](src/realworld/base/base-page.ts#L3) только хранит `Page`; [BaseApiClient](src/realworld/base/base-api-client.ts#L3) хранит контекст и формирует заголовок авторизации. Такая небольшая общая база подходит текущему масштабу. Её ценность — единый контракт, а не количество методов. Добавлять в неё универсальные `click`, `fill`, `wait` не нужно: они скроют полезные возможности Playwright и ухудшат диагностику.

**Проблемы.** Существенного нарушения разделения ответственности нет. Есть небольшая связанность: fixtures и specs импортируют данные окружения непосредственно из `playwright.config.ts` ([base-test.ts:3](src/realworld/base/base-test.ts#L3), [spec:3](src/realworld/tests/articles/us001-publish-article.spec.ts#L3)). Поэтому импорт тестовых данных также выполняет загрузку конфигурационного модуля. Сейчас это работает и не оправдывает отдельный рефакторинг.

**Что изменить и зачем.** Когда будет добавлена проверка окружения, можно вынести только разбор и валидацию `REAL_WORLD_PROJECT_DATA` в небольшой модуль конфигурации и импортировать его из config и fixtures. Это локальное уменьшение связанности, без нового архитектурного слоя. Отдельной задачей до этого заниматься не нужно.

**Как объяснить на собеседовании.** «Страницы отвечают за взаимодействие с UI, клиенты — за HTTP, сценарии — за бизнес-проверки, fixtures — за жизненный цикл ресурсов. Общие классы содержат только действительно общие вещи».

## 2. TypeScript, проверка типов, ESLint и Prettier

**Как работает.** Playwright загружает `.ts`-файлы и преобразует их для исполнения. В проекте нет `tsconfig`, зависимости `typescript`, команды `typecheck`, конфигурации или зависимостей ESLint и Prettier. Это подтверждено поиском файлов, `package.json` и lockfile. Установленные `tsc`, `eslint`, `prettier` также не найдены через `PATH`.

**Что хорошо.** Код использует явные типы для fixture-фабрик, конфигурации, payload и возвращаемых managers. В `BaseApiClient` правильно отражено, что JWT может отсутствовать. Зависимости тестового раннера закреплены, lockfile присутствует, `npm ci` используется и в Docker, и в запуске из исходников. Корневые `devDependencies` package и lockfile совпадают.

### F1. Нет отдельной проверки типов

**Статус: подтверждено по коду. Приоритет: исправить сейчас.**

**Место:** [package.json:6](package.json#L6), [workflow запуска из исходников:21](.github/workflows/run_test_from_branch.yml#L21).

**Ситуация:** изменение передаёт число вместо строки или использует несуществующее поле. Сбор и запуск Playwright сами по себе не являются проверкой типов. Ошибка может проявиться только в исполняемой ветке сценария. Успешный `--list` также не доказывает типовую корректность.

**Минимальное исправление:** добавить `typescript` как dev dependency, небольшой `tsconfig.json` с `strict: true` и `noEmit: true`, команду `typecheck: tsc --noEmit`; выполнять её до запуска браузеров. Например:

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "commonjs",
    "moduleResolution": "node",
    "strict": true,
    "noEmit": true,
    "esModuleInterop": true,
    "skipLibCheck": true,
    "types": ["node"]
  },
  "include": ["playwright.config.ts", "src/**/*.ts"]
}
```

Это стартовая конфигурация под существующий CommonJS-проект; её следует проверить установленной выбранной версией компилятора. Здесь компилятор не устанавливался и typecheck не выполнялся. Утверждения о наличии конкретных ошибок типов в текущем коде нет.

**ESLint и Prettier:** их отсутствие — optional-улучшение, а не причина объявлять фреймворк неработоспособным. В коде действительно различаются отступы, регистр имён полей (`Form.Email`, `titleInput`, `NewArticle`) и оформление `;` ([LoginPage.ts](src/realworld/ui/pages/LoginPage.ts#L5), [Navbar.ts](src/realworld/ui/components/Navbar.ts#L5)). Форматтер даст единый вид; lint с проверкой необработанных Promise полезен для предотвращения пропущенного `await`. Вводить большой набор правил и массово переписывать код ради стиля не требуется. По ценности для этого проекта typecheck идёт первым.

## 3. Конфигурация и переменные окружения

**Как работает.** `dotenv` загружает окружение, затем `REAL_WORLD_PROJECT_DATA` разбирается как JSON. В этой переменной находятся URL UI, URL API и список пользователей. `example.env` содержит пустой шаблон, а не рабочие значения. Реальные `.env` и содержимое `.auth` не изучались.

**Что хорошо.** Настройки не зашиты в specs. Есть локальные значения URL по умолчанию. `.env` и `.auth` исключены из Git, а `.dockerignore` также исключает `.env`, `.env.*` и `.auth`. В CI переменная передаётся через secrets, в контейнер — через окружение при запуске. По исходникам не обнаружена необходимость менять этот способ передачи конфигурации.

### F2. JSON объявлен типизированным, но фактически не проверяется

**Статус: подтверждено по коду и проверено локально. Приоритет: исправить сейчас.**

**Место:** [playwright.config.ts:18](playwright.config.ts#L18), [users.setup.ts:5](src/realworld/tests/users.setup.ts#L5), [spec:7](src/realworld/tests/articles/us001-publish-article.spec.ts#L7).

**Ситуация:** `JSON.parse` возвращает значение без гарантии соответствия `RealWorldProjectData`. Присваивание типу не проверяет JSON во время исполнения. Локальная загрузка config с заглушкой `dotenv` подтвердила, что отсутствующая переменная, `{}` и `{"users":"oops"}` принимаются самим config.

Setup проверяет только наличие ненулевой `users.length`. Он не проверяет, что это массив объектов с непустыми полями. В spec выражение `realWorldProjectData.users[0]` выполняется раньше проверки `publishingUser`: при отсутствующем `users` собственное поясняющее сообщение не поможет. Какую ошибку пользователь увидит первой при общем сборе, зависит от того, какой модуль будет загружен первым.

**Минимальное исправление:** разобрать значение как `unknown` и один раз проверить:

- объект верхнего уровня и непустой массив `users`;
- непустые строки `name`, `username`, `password` для каждого пользователя;
- уникальность aliases `name`, а также отсутствие случайного повторения учётных данных;
- корректность HTTP/HTTPS URL после применения согласованных локальных defaults.

Для трёх полей пользователя достаточно ручной проверки; отдельная библиотека валидации не обязательна. Ошибка должна называть переменную и поле, но не печатать весь JSON с паролями. Проверка должна происходить до регистрации и создания контекстов.

Поле `username` сейчас фактически хранит email, что прямо отмечено в [users.setup.ts:15](src/realworld/tests/users.setup.ts#L15); `name` используется и как alias, и как username при регистрации. Это работает, но название вводит в заблуждение. Переименование `username` → `email` полезно при следующем изменении контракта окружения; отдельно ломать уже работающий secret ради этого не требуется.

### F3. API URL зависит от завершающего слеша

**Статус: подтверждено по коду и проверено локально. Приоритет: исправить вместе с F2.**

**Место:** [base-test.ts:58](src/realworld/base/base-test.ts#L58), [ArticlesApiClient.ts:18](src/realworld/api/clients/ArticlesApiClient.ts#L18), аналогично URL в `UserApiClient`.

**Ситуация:** клиент использует относительный адрес `articles`. Для базы `https://host/api/` он разрешается в `https://host/api/articles`, для `https://host/api` — в `https://host/articles`. Это проверено через стандартный `new URL`, без сетевых запросов. Локальный fallback заканчивается слешем и корректен; какие реальные значения используются в окружении, не проверялось.

**Минимальное исправление:** после проверки URL нормализовать именно путь базы API и использовать результат во fixture:

```ts
const apiUrl = new URL(rawApiBaseUrl);
apiUrl.pathname = apiUrl.pathname.replace(/\/?$/, '/');
const apiBaseUrl = apiUrl.href;
```

Для базы API также стоит отклонять query/hash, если они не являются частью поддерживаемого формата. Альтернатива нормализации — явно требовать завершающий `/` и выдавать понятную ошибку. Менять методы клиентов на `/articles` нельзя: ведущий слеш отбросит префикс `/api/`.

## 4. Fixtures и managers

**Как работает.** [base-test.ts](src/realworld/base/base-test.ts#L31) предоставляет две фабрики: `createPageManagerAs` и `createApiManagerAs`. Для каждого вызова создаётся новый контекст, который сохраняется в список и закрывается после `use`. Браузер при этом может оставаться общим worker-ресурсом. Managers создают страницы и клиентов лениво через `??=`.

**Что хорошо.** Один тест может получить две независимые UI-сессии разных пользователей. Тестам не нужно вручную закрывать контексты. API-сценарий, использующий только API-фабрику, не требует UI-контекста в своём теле. Завершение API-контекстов через `dispose()` проверено локально на заглушках.

Ручной `browser.newContext()` здесь не означает потерю `baseURL`, параметров Desktop Chrome или диагностики. В установленном Playwright 1.64.1 обработчик создания контекста дополняет отсутствующие options параметрами проекта и подключает запись артефактов. Это проверено чтением реализации в `node_modules/playwright/lib/index.js` (обработчики на строках 122–160). Поэтому замечание «`page.goto('/')` заведомо не работает без явного `baseURL` в фабрике» было бы неверным. Фактический запуск браузера и получение артефактов здесь не проверялись.

Фабрика UI передаёт ключ `storageState` даже для `null`, со значением `undefined`. В этой версии Playwright унаследованное значение не подставляется при уже присутствующем ключе. Поэтому по коду нет основания утверждать, что `createPageManagerAs(null)` автоматически становится первым пользователем.

### F4. API-фабрика неявно получает storage state первого пользователя

**Статус: подтверждено по исходникам проекта и установленного Playwright. Приоритет: исправить сейчас вместе с контрактом авторизации.**

**Место:** [playwright.config.ts:55](playwright.config.ts#L55), [base-test.ts:57](src/realworld/base/base-test.ts#L57).

**Ситуация:** в проекте `realworld` установлен общий `storageState` первого пользователя. API-фабрика передаёт только `baseURL`. В Playwright 1.64.1 настройки проекта дополняют также options `request.newContext()`, после чего строковый путь storage state читается при создании API-контекста (`node_modules/playwright-core/lib/coreBundle.js:60699`).

В результате даже `createApiManagerAs(null)` зависит от наличия файла первого пользователя; контекст другого пользователя также получает этот state, хотя JWT для заголовка берётся из отдельного файла выбранного пользователя.

Это **не доказательство утечки JWT в анонимный запрос**: localStorage сам по себе не формирует `Authorization`, а клиент добавляет заголовок только при наличии переданного token. Но зависимость от чужого файла подтверждена; если в state появятся cookies, они тоже попадут в API-контекст. Состав реальных state-файлов не проверялся.

**Минимальное исправление:** поскольку API здесь авторизуется явным заголовком, задать пустой state для API-контекстов:

```ts
const context = await request.newContext({
  baseURL: apiBaseUrl,
  storageState: { cookies: [], origins: [] },
});
```

Другой небольшой вариант — убрать общий `storageState` из проекта `realworld`: все текущие сценарии и так выбирают пользователя через фабрики. Достаточно выбрать один последовательный способ; внедрять оба изменения обязательно не нужно.

**Managers подходят масштабу проекта.** [RealWorldPageManager](src/realworld/ui/RealWorldPageManager.ts#L26) и [ApiManager](src/realworld/api/ApiManager.ts#L17) содержат только ленивые getters и зависимости. Это удобная точка получения объектов и выбора пользователя. Их не нужно заменять DI-контейнером. Публичный `pm.page` уместен для URL assertions, перехватов сети и сохранения state — скрывать весь API Playwright за методами страниц здесь было бы неудобно.

## 5. Setup, авторизация и storage state

**Как работает.** [users.setup.ts](src/realworld/tests/users.setup.ts#L9) регистрирует каждого пользователя из config через UI, ожидает `New Article` и сохраняет browser storage state. Основной проект зависит от setup. Для API JWT читается из localStorage-записи `jwtToken` и передаётся как `Authorization: Token ...`.

**Что хорошо.** Это project dependency, поэтому подготовка видна как тесты и шаги в отчёте, а не спрятана во внешнем скрипте. Состояние сохраняется после ожидаемого признака авторизации. Основные UI-тесты не повторяют login, каждый загружает state в новый контекст. Файлы авторизации не перечислены среди CI-артефактов и исключены из Git и Docker build context соответствующими ignore-правилами.

**Регистрация намеренная и обоснована контекстом владельца.** Если публичное демо удаляет пользователей, обычный login со старой парой credentials не восстановит предусловие. Смена регистрации на «сначала login, затем register при ошибке» усложнила бы setup без подтверждённой пользы. Делать это рекомендацией аудита оснований нет. Утверждения о повторной регистрации и удалении данных получены от владельца; собственных запросов для их проверки не выполнялось.

### F5. Запрошенная авторизованная API-сессия может молча стать анонимной

**Статус: подтверждено по коду и проверено локально на синтетическом state. Приоритет: исправить сейчас.**

**Место:** [base-test.ts:14](src/realworld/base/base-test.ts#L14), [base-test.ts:55](src/realworld/base/base-test.ts#L55), [base-api-client.ts:12](src/realworld/base/base-api-client.ts#L12).

**Ситуация:** файл корректный JSON, но в нём нет `jwtToken` — например, изменился ключ приложения или state сохранён без авторизации. `extractToken()` возвращает `null`; `createApiManagerAs('user1')` создаёт manager без токена, а клиент отправляет запрос без заголовка. Ошибка выглядит как API-регрессия с `401`, хотя нарушено предусловие теста.

На заглушках подтверждено и другое поведение: функция принимает первый найденный `jwtToken` из любого origin. Сам по себе чужой origin в настоящих state-файлах не обнаружен, поскольку они не читались. Это ограничение алгоритма, а не утверждение о текущих файлах.

**Минимальное исправление:** выбирать origin, соответствующий `new URL(baseUrl).origin`, и для именованного пользователя требовать непустой JWT. При отсутствии — завершать подготовку понятной ошибкой с alias пользователя, без значения токена. Например, после извлечения:

```ts
if (userName && !token) {
  throw new Error(`JWT не найден в storage state пользователя ${userName}`);
}
```

Для `null` отсутствие JWT, наоборот, является ожидаемым состоянием. Дополнительно полезно проверять наличие JWT перед сохранением результата setup, но это не заменяет защиту API-фабрики. Отдельный HTTP-запрос проверки JWT перед каждым тестом сейчас не нужен: он добавит сетевую зависимость, а удаление пользователя внешним демо всё равно возможно после проверки.

**Риск параллельных прогонов, требует запуска.** `workers: 1` ограничивает только один CI-run. Два ручных workflow могут одновременно использовать тех же пользователей. С учётом описанного владельцем пересоздания аккаунта один setup потенциально нарушит предусловия другого прогона. Это не воспроизведено; новый пользователь на каждый тест не предлагается. Если конфликт наблюдается, минимально полезно сериализовать именно прогоны, использующие один набор аккаунтов, либо выделить разные наборы для одновременно запускаемых workflows.

**Как объяснить на собеседовании.** «Setup восстанавливает предусловия нестабильного публичного стенда; storage state ускоряет последующие тесты, а новый BrowserContext изолирует их браузерное состояние. Изоляция браузера не гарантирует изоляцию серверных данных».

## 6. Page Objects и локаторы

**Как работает.** Объекты страниц описывают элементы через Playwright `Locator`. Сценарий получает их через manager и выполняет действия. Повторяемые последовательности вынесены в `register`, `login`, `addTag`.

**Что хорошо.** В приоритете role и placeholder, а не XPath и длинные цепочки DOM. Locator вычисляется при действии, поэтому поля Page Object не являются устаревающими element handles после навигации. `addTag` — полезный предметный метод; доступ к отдельным полям формы при этом сохранён. Нет обёрток, которые отключают auto-wait Playwright или скрывают assertions.

**Ограничения текущих объектов, без необходимости срочного рефакторинга:**

- [ArticleViewPage.ts:6](src/realworld/ui/pages/ArticleViewPage.ts#L6): `body = '.article-content p'` описывает параграфы, а не весь Markdown-контент. Для существующего одного параграфа это соответствует сценарию. При нескольких параграфах строковый `toHaveText` на множественном locator станет проблемой; заголовки и списки этот locator вообще не проверит. Расширять объект стоит при первом сценарии с таким содержимым, выбрав проверенный контейнер текста статьи.
- [ArticleViewPage.ts:8](src/realworld/ui/pages/ArticleViewPage.ts#L8): `.first()` для Edit/Delete допустим, если это намеренный выбор из повторённых панелей. Он также скроет неожиданное появление лишнего совпадения. Без live DOM нельзя объявлять это дефектом. При расширении проверок лучше ограничить locator нужной панелью, если для неё есть устойчивый ориентир.
- [HomePage.ts:9](src/realworld/ui/pages/HomePage.ts#L9): `hasText: title` ищет подстроку по всей карточке. Для текущего уникального заголовка риск невелик. Если тест начнёт различать похожие заголовки, фильтровать нужно по точному heading карточки; структуру heading следует сначала проверить на приложении.
- [RegisterPage.ts:7](src/realworld/ui/pages/RegisterPage.ts#L7) и [LoginPage.ts:7](src/realworld/ui/pages/LoginPage.ts#L7): пароль ищется как `textbox`. У обычного `input[type=password]` нет неявной роли `textbox`; locator сработает только при подходящей фактической разметке/роли. DOM в этом аудите не исследовался, поэтому это **пункт для проверки, а не подтверждённое падение setup**. Если поле — обычный password input, использовать проверенный label или placeholder. Менять selector вслепую нельзя.

CSS для tag chips сам по себе не проблема: это не случайные сгенерированные классы по данным кода. Приоритет сейчас — корректность выбранного элемента, а не достижение полного запрета CSS.

## 7. API clients и assertions API

**Как работает.** `UserApiClient` предоставляет login/register/get/update. `ArticlesApiClient` пока содержит только создание статьи. Методы возвращают `APIResponse`, не навязывая конкретный ожидаемый статус. Общий клиент централизует формат заголовка `Token`.

**Что хорошо.** Клиенты небольшие, тело запроса соответствует форме `{ user: ... }` / `{ article: ... }` из локального OpenAPI. Отсутствующие tags преобразуются в пустой список, но явно переданный `tagList` сохраняется благодаря порядку spread ([ArticlesApiClient.ts:17](src/realworld/api/clients/ArticlesApiClient.ts#L17)). Это нормально для текущих валидных запросов.

Тест [A006](src/realworld/tests/articles/us001-publish-article.spec.ts#L65) проверяет не только `401`, но и структуру ошибки. Тест [A010](src/realworld/tests/articles/us001-publish-article.spec.ts#L82) проверяет отправленные поля, tags, даты как строки, признаки favorite и профиль автора с nullable `bio`/`image`. Для сценария принятия заголовка это полезнее одной проверки `201`.

**Что полезно уточнить:**

1. **Автор проверяется слишком широко.** В [spec:110](src/realworld/tests/articles/us001-publish-article.spec.ts#L110) допускается любой строковый `author.username`. Если запрос создаст статью от другого пользователя, тест останется зелёным. По [setup:16](src/realworld/tests/users.setup.ts#L16) username регистрируется как `publishingUser.name`, поэтому минимальное усиление существующего теста:

   ```ts
   expect(responseBody.article.author.username).toBe(publishingUser.name);
   ```

   Это подтверждённый пробел проверки принадлежности, а не обнаруженное создание статьи от чужого имени.

2. **В A010 JSON разбирается раньше проверки статуса.** [spec:92](src/realworld/tests/articles/us001-publish-article.spec.ts#L92). Если gateway вернёт `502` с HTML, вместо понятного сравнения статусов будет ошибка парсинга, а attachment не появится. Минимально: сначала получить/приложить текст ответа и проверить статус, затем разбирать JSON. В A006 статус уже проверяется первым. Не требуется отдельная система логирования HTTP.

3. **Тип ответа и runtime-контракт — разные проверки.** `response.json()` не даёт гарантий структуры во время исполнения. Уже существующие assertions нужны даже после F1. При этом `expect.any(String)` для дат не проверяет `date-time`, а для slug — непустоту. Для данного boundary-сценария полный OpenAPI validator необязателен; эти проверки следует добавлять только при заявленной цели проверять весь контракт.

4. **Валидный payload намеренно строгий.** `NewArticlePayload` требует все обязательные поля. Для текущих тестов это правильно. Если будет выбран сценарий отсутствующего поля, нельзя просто ослаблять основной тип для всех вызовов или разбрасывать `as any` по specs. Тогда понадобится небольшой явно обозначенный способ отправить некорректное тело. До выбора такого сценария расширять клиент незачем.

Локально отдельно проверено поведение matcher: `toMatchObject({ article: { tagList: [] } })` отклоняет непустой массив. Утверждение, что существующая проверка пустых tags вообще ничего не проверяет, было бы неверным.

## 8. Изоляция тестов, создание и очистка данных

**Как работает.** Контексты создаются заново, а опубликованные статьи получают заголовки с `Date.now()`. UI- и API-тесты не используют статью, созданную соседним тестом. Авторизованные сценарии используют одного publishing user.

**Что хорошо.** Нет зависимости вида «второй тест должен идти после первого». Имена статей у UI и API имеют разные префиксы. Для текущих трёх сценариев этого достаточно, чтобы избежать обычных конфликтов заголовков внутри одного прогона. `Date.now()` не является строгой гарантией уникальности между процессами, но вводить сложный генератор данных ради этих тестов не нужно; при необходимости достаточно `randomUUID()`.

### F6. Успешные тесты оставляют созданные статьи

**Статус: подтверждено по коду. Приоритет: исправить сейчас.**

**Место:** [UI-тест:49](src/realworld/tests/articles/us001-publish-article.spec.ts#L49), [API-тест:87](src/realworld/tests/articles/us001-publish-article.spec.ts#L87), [ArticlesApiClient.ts](src/realworld/api/clients/ArticlesApiClient.ts#L11).

**Ситуация:** при успешном прогоне создаются две статьи. Удаления, teardown данных и метода удаления в клиенте нет. Если UI-тест упадёт уже после успешной публикации, статья также останется. Закрытие BrowserContext и `APIRequestContext.dispose()` удаляет локальные ресурсы, но не статьи на сервере.

При retries успешная публикация может произойти несколько раз, если падает последующая проверка ленты. Внешнее удаление данных демо не гарантирует, когда исчезнут именно эти статьи. Оно не является управляемой очисткой теста.

**Минимальное исправление:** добавить метод удаления в существующий `ArticlesApiClient`, без нового слоя:

```ts
deleteArticle(slug: string) {
  return this.request.delete(`articles/${encodeURIComponent(slug)}`, {
    headers: this.authHeaders(),
  });
}
```

Успешный `DELETE /articles/{slug}` со статусом `204` описан в [локальном OpenAPI:284](docs/realworld/openapi.yml#L284); фактическая работа удаления на стенде здесь не проверялась.

Для обоих создающих тестов сохранить slug сразу после успешного создания, **до остальных assertions**, и удалять только эту статью в `finally` либо test-scoped teardown. В UI-тесте slug можно получить из ответа публикации; ожидание ответа регистрируется до клика. Если брать slug только после проверки всей страницы, падение ранней проверки снова оставит данные.

Очистку делать API-запросом: она не должна повторять UI-путь удаления, который не является предметом этих тестов. Проверять `204`; `404` допустим как «статья уже отсутствует», если такой контракт подтверждён на используемом стенде. Ошибки очистки нужно показывать отдельно, сохраняя исходную причину падения. Массовое удаление статей по общему префиксу и удаление пользователей здесь не нужны.

**Риск внешней ленты, требует запуска.** Global Feed — общий ресурс. Статья может уйти со страницы из-за активности других пользователей или исчезнуть при очистке демо. Это потенциальный источник нестабильности, а не доказанный текущий flake. Заменять проверку global feed на API-поиск нельзя: это изменит предмет E2E-сценария. Если проблема воспроизводится, сначала зафиксировать ответ ленты и пагинацию в trace, затем выбирать решение.

## 9. Сценарии, assertions и соответствие тест-кейсам

**Как работает.** В одном spec есть один `@E2E` и два `@Extended`. Идентификаторы совпадают с описанными тест-кейсами. Setup создаёт отдельный тест для каждого настроенного пользователя и не является дополнительным покрытием бизнес-сценариев публикации.

| Тест | Реальное покрытие | Соответствие описанию |
|---|---|---|
| US001-TC-019 | Авторизованный пользователь открывает форму, заполняет поля, добавляет tag, публикует, видит контент и свои controls, находит статью в global feed | Основной путь реализован. Redirect проверяется только косвенно через элементы страницы; URL не проверяется |
| US001-TC-A006 | POST без явно добавленного Authorization возвращает 401 и ожидаемую структуру ошибки | Соответствует шагу тест-кейса; структура ошибки — дополнительная проверка по локальной документации. Неявный storage state см. F4 |
| US001-TC-A010 | POST с заголовком длиной 100 символов возвращает 201 и ожидаемые поля | Соответствует выбранному позитивному примеру. Не доказывает максимальную разрешённую длину |

### F7. Redirect из UI-кейса не проверяется явно

**Статус: подтверждено по коду. Приоритет: небольшое исправление существующего теста.**

**Место:** [UI test-case:476](test-cases/realworld/articles/US-001/ui/test-cases.md#L476), [UI test-case:479](test-cases/realworld/articles/US-001/ui/test-cases.md#L479), [spec:25](src/realworld/tests/articles/us001-publish-article.spec.ts#L25), [spec:49](src/realworld/tests/articles/us001-publish-article.spec.ts#L49).

**Ситуация:** приложение показывает редактор или содержимое статьи, но оставляет неверный URL. Сейчас тест может пройти, хотя ожидаемые `/editor` и `/article/{slug}` не установлены. Наличие heading не заменяет проверку маршрута.

**Минимальное исправление:** добавить `toHaveURL` после открытия редактора и публикации, согласовав точный шаблон с фактическим роутингом приложения. Для маршрутов из тест-кейса, например:

```ts
await expect(pm.page).toHaveURL(/\/editor$/);
// После публикации:
await expect(pm.page).toHaveURL(/\/article\/[^/?#]+$/);
```

Не нужен новый тест: assertions дополняют существующий сценарий.

### F8. Документированное покрытие шире автоматизированного, а граница Title противоречива

**Статус: подтверждено по исходникам. Приоритет: прояснить сейчас; не расширять suite автоматически.**

**Место:** [UI coverage summary:513](test-cases/realworld/articles/US-001/ui/test-cases.md#L513), [API coverage summary:291](test-cases/realworld/articles/US-001/api/test-cases.md#L291), [User Story v2:16](user-stories/realworld/US-001-publish-article-v2.md#L16), [User Story v2:42](user-stories/realworld/US-001-publish-article-v2.md#L42).

В документах описаны 19 UI- и 11 API-кейсов. Исполняются 1 UI- и 2 API-кейса: 3/30, то есть 10% по числу кейсов. Этот процент не измеряет полноту продуктовых требований, ценность E2E или качество тестов. Матрицы в документах описывают **спроектированные проверки**, а не факт их выполнения. Называть текущую автоматизацию покрытием 19/20 AC нельзя.

В v2 одновременно указаны Title max 100 в таблице и hard cap 255 в AC-12. Противоречие уже отмечено в тест-кейсах. OpenAPI не содержит `maxLength` для `NewArticle.title` ([openapi.yml:579](docs/realworld/openapi.yml#L579)). A010 успешно принимает 100 символов и потому совместим с обоими вариантами ограничения. Он не подтверждает, что 101 должен отклоняться.

**Минимальное полезное действие:** явно различать «спроектирован» и «автоматизирован», а перед автоматизацией A011/TC-008 согласовать одну границу Title. Не менять ожидание теста под фактический ответ сервера без решения о требовании. Сейчас достаточно компактного списка трёх реализованных IDs; отдельная система управления покрытием не нужна.

**Проверка времени ленты:** [AC-15](user-stories/realworld/US-001-publish-article-v2.md#L47) и отдельный TC-018 требуют появления за 2 секунды. TC-019 проверяет появление статьи, но его шаги не задают собственный таймер 2 секунды. В текущем коде после публикации сначала выполняются проверки страницы, затем переходы и обычный `toBeVisible`. Поэтому прохождение E2E не доказывает SLA из AC-15. Просто добавить `{ timeout: 2000 }` к последнему assertion недостаточно: отсчёт начнётся слишком поздно. Для этого публичного стенда разумно сохранить E2E как функциональную проверку и явно не заявлять измерение SLA; отдельную временную проверку отложить до контролируемого окружения и согласованного способа измерения.

Наличие у автора Edit/Delete покрывает только положительную часть авторизации. Отсутствие controls у другого пользователя описано в отдельном TC-016 и пока не автоматизировано. Это следует честно обозначать, но второй UI-пользователь не нужен каждому happy-path тесту.

## 10. Запуск, ожидания, retries и диагностика

**Как работает.** [playwright.config.ts:25](playwright.config.ts#L25) включает `fullyParallel`; локально worker count выбирает Playwright, в CI используется один worker. В CI разрешены две повторные попытки, локально — ни одной. `forbidOnly` включён в CI. Настроены screenshots при падении и trace на первом retry. Timeouts явно не переопределены; стандартный test timeout установленного раннера — 30 секунд.

**Что хорошо.** В коде нет `waitForTimeout` и ручного polling DOM. `fill`, `click` и web-first assertions используют ожидания Playwright. Сценарий разбит на предметные `test.step`, что облегчает чтение HTML и Allure. Retries ограничены и отличаются для CI и локальной разработки. Для трёх тестов один CI-worker — разумный выбор: выигрыш от распараллеливания невелик, конкуренция на публичном демо увеличится.

Одновременные `fullyParallel: true` и `workers: 1` не конфликтуют: первая настройка разрешает независимое планирование тестов, вторая ограничивает число исполняющих workers в CI. Последовательность бизнес-тестам не требуется. В `testDir: './src'` нет практической проблемы: `testMatch` отдельно ограничивает setup и specs.

**Что полезно изменить:**

- **Локальная диагностика ограничена.** При `retries: 0` и `trace: 'on-first-retry'` обычное локальное падение будет без trace. Это подтверждается сочетанием настроек, а не попыткой воспроизвести падение. Для разового расследования достаточно `--trace=retain-on-failure`; если локальная отладка частая — сделать этот режим локальным default. Постоянно включать видео и trace всех успешных тестов незачем.
- **Retry не восстанавливает серверные предусловия.** При повторе основного теста setup dependency не становится автоматическим механизмом повторной регистрации пользователя. Если демо удалило аккаунт между setup и тестом, повтор с тем же state может снова упасть. Это риск внешнего окружения, а не основание добавлять скрытый relogin в каждое действие. Сначала различать в диагностике ошибку предусловия и продуктовый дефект.
- **Повторы увеличивают потребность в cleanup.** Повтор после успешного POST и неуспешного assertion создаёт новую статью. Поэтому F6 полезнее увеличения retries или всех timeouts.

Увеличивать глобальные timeouts без измеренной причины не предлагается. Нестабильную ленту, удаление данных и неработающий locator это не исправит.

## 11. Docker, GitHub Actions, GHCR и отчёты

**Как работает.** [Dockerfile](Dockerfile#L1) устанавливает Node 24, зависимости по lockfile и Chromium с системными зависимостями. Контейнер запускает `allure run -- npm test`. Build workflow публикует образ на push в `master` с тегами `latest` и commit SHA. Два ручных workflow запускают тесты из исходников или образа, сохраняют HTML/Allure и диагностические файлы, затем публикуют страницу выбора отчёта.

**Что хорошо и подходит масштабу:**

- `npm ci` и установка браузера из той же версии Playwright дают воспроизводимую связку пакета и Chromium. Переход на другой базовый Docker image не требуется только ради соответствия шаблону.
- Установка зависимостей выделена до `COPY . .`, что позволяет использовать Docker cache при изменении specs.
- `--init` и `--ipc=host` в контейнерном workflow — уместные параметры для Chromium. Отчёты выводятся в bind mounts и переживают `--rm`.
- Есть SHA-тег образа: для воспроизведения конкретной версии можно выбрать его вместо изменяемого `latest`.
- Отсутствие checkout в build job само по себе не ошибка: `docker/build-push-action` без явно заданного локального context использует Git context. Рекомендация обязательно добавить checkout здесь не обоснована текущим кодом.
- Условия `!cancelled()` позволяют собирать отчёты при падении тестов. Отдельный publish job зависит от факта загрузки Pages artifact. На обычном завершившемся тестовом прогоне эта схема разумна.
- Retention артефактов 3 дня и одна страница последнего отчёта достаточны для демонстрации. Обязательная история Allure или отдельный сервер отчётов не нужны.

Ручные запуски соответствуют портфолио-демонстрации. Это не автоматический PR quality gate, но объявлять отсутствие такого gate неисправностью существующего pipeline оснований нет. Добавить лёгкий typecheck в уже используемый путь запуска полезнее перестройки CI.

### F9. При раннем сбое можно опубликовать страницу без отчётов

**Статус: подтверждено по условиям workflow; запуск аварийного workflow не выполнялся. Приоритет: небольшое улучшение CI.**

**Место:** [source workflow:31](.github/workflows/run_test_from_branch.yml#L31), [source workflow:49](.github/workflows/run_test_from_branch.yml#L49), [container workflow:57](.github/workflows/run_tests_from_container.yml#L57), [container workflow:75](.github/workflows/run_tests_from_container.yml#L75).

**Ситуация:** checkout успешен, но установка пакетов или pull образа завершились ошибкой до генерации отчётов. `Prepare Reports` всё равно запускается и пытается перенести отсутствующие каталоги. После его падения шаг `upload-pages-artifact` также разрешён через `!cancelled()`. В каталоге `reports` уже есть отслеживаемый `index.html`, поэтому может загрузиться валидный Pages artifact только с этой страницей. Publish job ориентируется на успех загрузки artifact и может заменить предыдущую публикацию страницей с неработающими ссылками.

Сбой `mv` при отсутствующем каталоге и отсутствие проверки готовых HTML видны по коду. Фактическая замена опубликованного сайта в таком сценарии не проверялась; успешные обычные прогоны этим замечанием не оспариваются.

**Минимальное исправление:** в подготовке отдельно проверить наличие входных HTML обоих отчётов, переносить существующее без дополнительной ошибки и выставлять output, например `ready=true`, только при готовом комплекте. Шаг загрузки Pages artifact выполнять по этому output. Upload диагностических artifacts оставить доступным после падения тестов; при неполной подготовке сохранять существующие исходные каталоги отчётов как artifacts.

Проверка должна зависеть от готовности отчётов, **а не от зелёного статуса тестов**: отчёт о неуспешном тестовом прогоне тоже нужно публиковать. Если отчётов ещё нет, достаточно сохранить диагностику раннего сбоя и не затирать последнюю полноценную публикацию.

Других обязательных изменений Docker/GHCR/HTML/Allure/Pages по изученному коду не предлагается. В этом аудите образы не собирались, workflows не запускались и фактические внешние публикации не проверялись.
